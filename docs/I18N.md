# How the translations work

Allium Assault speaks English, German, Croatian and Mandarin. This page is how to add a string, add
a language, and understand why the pieces sit where they do.

## The shape of it

Two modules, both in `src/ui`:

| File             | Holds                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------- |
| `i18n.ts`        | 188 interface strings per language, the `t()` lookup, and which language is current    |
| `i18nWeapons.ts` | The 23 weapons' names and descriptions, which grow with the arsenal rather than the UI |

They are split because they change for different reasons. A new screen adds keys to the first; a
new weapon adds an entry to the second.

**English is the source of truth.** `EN` is a `const` object and `TextKey` is `keyof typeof EN`, so
the compiler knows every key that exists and refuses one that does not. The other three catalogues
are `Partial<Record<TextKey, string>>`: a missing key falls back to the English rather than showing
an identifier, which means a half-finished language is half-translated instead of broken.

The weapons work the other way round, and deliberately. Their English lives in
`src/core/weapons.ts`, where a weapon is defined; `i18nWeapons.ts` carries only the other three
languages and falls back to the weapon table. Nothing is written twice.

## Using a string

```ts
import { t } from './i18n';

t('setup.start'); // "Start Battle ▶"
t('victory.wins', { name: 'Ruby' }); // "Ruby wins!"
```

Placeholders are `{name}` and are filled from the second argument. A placeholder with nothing to
fill it is left as written, which shows up in a screenshot far more usefully than a blank would.

Weapon names and blurbs come from their own helpers, never from `WEAPONS[id].name`:

```ts
import { weaponBlurb, weaponName } from './i18nWeapons';
```

## Adding a string

1. Add the key to `EN` in `i18n.ts`. Group it by screen — `setup.`, `hud.`, `award.` and so on.
2. Add it to `DE`, `HR` and `ZH`. The test below will tell you if you forget.
3. Use `t('your.key')` in the markup. Never write the English inline "for now": the sweep in
   `tests/docs.test.ts` and the German browser test are what catch that, and they catch it late.

## Adding a language

1. Add it to the `Language` union and to `LANGUAGES`, labelled in its own words — that is how a
   player finds their own language in a list they cannot read.
2. Write the catalogue, and the weapon words in `i18nWeapons.ts`.
3. Nothing else. The setup screen builds its language control from `LANGUAGES`, the settings
   validate against it, and `preferredLanguage()` will match the browser's tag automatically.

## What the rules may not do

**The core never holds a player-facing sentence.** `src/core` has no access to the catalogue and
must not grow one. Where the rules need to say something, they emit an id and the numbers behind it
and let the interface phrase it. The end-of-match awards are the worked example:

```ts
// src/core/stats.ts — an id, who earned it, and the numbers
{ id: 'mvp', icon: '🏅', who: 'Ruby', values: { damage: 240 }, tone: 'good' }
```

```ts
// src/ui — the words
t(`award.${a.id}.title`); // "Most Valuable Buddy"
t(`award.${a.id}.detail`, a.values); // "240 damage dealt"
```

This is not a style preference. The scoreboard shipped in 1.65.0 with its sentences built in the
core and was English in all four languages until 1.69.0, because there was nowhere for a translation
to go.

## Where the language is kept

In `localStorage` with the other settings, at schema version 3. The first time a player arrives
there is nothing stored, so `preferredLanguage(navigator.languages)` picks from the browser — `de-AT`
gives German, `zh-Hans-CN` and `cmn` both give Mandarin, anything unknown gives English.

Changing the language repaints whichever screen is open. The HUD is the exception worth knowing
about: it writes its fixed chrome once rather than every frame, so it rebuilds that chrome in
`attach()`, which is the only moment the language can have changed since it was last built.

## What the tests enforce

| Test                         | Fails when                                                               |
| ---------------------------- | ------------------------------------------------------------------------ |
| `i18n` — every key           | a language is missing any key, or any weapon's name or blurb             |
| `i18n` — actually different  | two languages give identical text where they should differ               |
| `i18n` — placeholders        | `{name}` is not filled, or is dropped when nothing is passed for it      |
| `i18n` — browser language    | `de-AT`, `zh-Hans-CN` or `cmn` do not resolve to the right catalogue     |
| `e2e` — languages            | the setup screen, HUD, weapon bar or name tags do not follow the setting |
| `e2e` — scoreboard in German | one English heading, award title or column name survives on the screen   |

## Where the words for a thing live

A string that describes the _interface_ goes in the catalogue. A string that names a _thing the game
defines_ keeps its English where the thing is defined, and the catalogue carries only the
translations:

| Thing              | English lives in      | Translations in  |
| ------------------ | --------------------- | ---------------- |
| Interface text     | `i18n.ts` (`EN`)      | `i18n.ts`        |
| Weapons            | `core/weapons.ts`     | `i18nWeapons.ts` |
| Sceneries, options | `i18n.ts` under a key | `i18n.ts`        |

Option values were the one place this went wrong. They come from data modules — `presets.ts`,
`settings.ts`, `quality.ts` — rather than from markup, so a sweep of the templates never saw them
and the setup screen showed Mandarin labels above English buttons for two releases. They carry a
`key: TextKey` now, and the screen resolves it at render time; the arrays must not call `t()`
themselves, because a module evaluated once would freeze whichever language was current at load.

## What stays in English on purpose

Physical key names (`Enter`, `Space`, `Backspace`), because that is what is printed on the keyboard;
proper nouns; URLs; licence identifiers; and the component names in the About screen's table.

Also the default team and buddy names — `Garlic Gang`, `Clovis`, `Sprout`. They are names rather
than interface text, the player can change any of them, and they are saved with the match config:
translating them would mean a team you had named quietly renaming itself when you switched
language.
